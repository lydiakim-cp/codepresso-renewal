# 디자인 QA — 시니어 UX/UI 디자이너 시점 검증

> **작업을 마친 뒤 연다.** [css-patterns.md](../css-patterns.md) 4번이 "어떻게 만드는가"라면,
> 이 문서는 **"만들어 놓은 것이 실제로 좋은가"** 를 다시 보는 검수 절차다.
>
> 관점은 **토스(Toss)식**이다 — 화려함이 아니라 **위계·리듬·의도**로 본다.
> "예쁜가"가 아니라 **"사용자가 어디를 먼저 보는지 내가 통제하고 있는가"** 를 묻는다.

구현자 시점에서 한 번 더 보는 것으로는 부족하다. **만든 사람은 자기 화면에 익숙해져서
평평함을 못 본다.** 그래서 아래를 **값으로 세어** 확인한다 — 눈으로 "괜찮아 보인다"로 넘기지 않는다.

## 0. 검수 방법 — 눈이 아니라 값으로

정적 서버로 띄우고(`partials/` 때문에 `file://`은 안 된다) **1440 / 900 / 560px** 세 폭에서 본다.

1. **스크롤을 끝까지 내리며 한 번 본다.** 이때 "어느 구간이 기억나는가"를 스스로 답한다.
   기억나는 구간이 **하나도 없으면 강조가 없는 것**이고, **전부 기억나면 강조가 너무 많은 것**이다.
2. 아래 5개 항목을 **세어서** 기록한다. 기준을 벗어나면 고친다.
3. 고치지 않기로 한 항목은 **왜 그대로 두는지** 보고에 남긴다.

## 1. 강조 섹션 — 페이지에 반드시 있어야 한다

**흰 면만 이어지는 페이지는 미완성이다.** 사용자의 시선이 쉬는 곳이 없고, 무엇이 중요한지
페이지가 말해주지 않는다.

**기준 (실측 — 현재 세 페이지가 이 방식이다)**

| 항목 | 기준 |
|---|---|
| 어두운 판(`--color-ink-heaviest`) | **페이지당 1~2곳.** 0곳이면 강조가 없는 것, 3곳 이상이면 강조가 죽는다 |
| 그중 하나 | 최하단 `cta-final`이 **이미 어둡다** — 이건 세는 데 포함한다 |
| 본문 중간 강조 | `outcomes.is-dark` 처럼 **성과·수치 구간 1곳**이 표준 |
| 어두운 판 2곳 사이 | **반드시 흰 면 섹션을 하나 둔다** — 안 그러면 페이지가 두 번 닫히는 느낌이 난다 |

```bash
# 어두운 판이 몇 곳인지 센다
# is-dark 모디파이어 + 자체가 어두운 컴포넌트(cta-final)를 함께 센다
grep -oE '<section class="[^"]*(is-dark|cta-final)[^"]*"' {페이지}.html | wc -l
```

> **`is-dark`만 세지 않는다.** 최하단 `cta-final`은 모디파이어 없이
> **컴포넌트 자체가** `--color-ink-heaviest`를 칠한다. `is-dark`만 세면
> index.html이 "강조 0곳"으로 보이지만 실제로는 1곳이다.

- **옅은 톤으로 강조를 만들려 하지 않는다.** `--color-surface-sunken`과 `--color-brand-tint-1`은
  **같은 색(#F5F8FF)** 이고 흰색과 6% 차이뿐이다. 그 둘로는 강조가 서지 않는다
  (실측 대비비 표 → [css-patterns.md](../css-patterns.md) 4번).
- 옅은 면이 필요하면 **`--color-brand-tint-2`**, 강조는 **어두운 판**이다. 이 둘만 쓴다.

## 2. width 100% 강조 배경 — 화면 끝까지 닿는가

**강조 구간의 배경은 좌우 끝까지 닿아야 한다.** 배경이 콘텐츠 폭(1320px)에서 잘리면
가운데 뜬 카드처럼 보여서, 화면을 구간으로 나누는 역할을 못 한다.

**이 프로젝트의 구조가 이미 그렇게 되어 있다:**

```
<section>        ← 배경은 여기가 그린다. 폭 제한이 없어 화면 끝까지 닿는다
  .section-wrap  ← 콘텐츠 폭(--container-medium 1320px) + 좌우 padding
```

```css
/* 좋음 — 섹션이 칠하므로 화면 끝까지 */
.outcomes.is-dark { background-color: var(--color-ink-heaviest); }

/* 나쁨 — 1320px에서 잘려 가운데 띠처럼 보인다 */
.outcomes .section-wrap { background-color: var(--color-ink-heaviest); }
```

**확인 방법** — 브라우저에서 강조 섹션의 배경 요소를 잡아 **폭이 뷰포트와 같은지** 잰다.

```js
// 콘솔에서 — 강조 섹션의 배경이 화면 끝까지 닿는가
const s = document.querySelector('.is-dark, .cta-final');
console.log(s.getBoundingClientRect().width, window.innerWidth); // 두 값이 같아야 한다
```

- **`.section-wrap`에 `background`를 주지 않는다.** 현재 프로젝트에 그런 사례가 하나도 없다 — 이 규칙을 깨는 첫 사례가 되지 않게 한다.
- 배경 이미지·그라디언트도 마찬가지로 `<section>`(또는 그 `::before`)이 그린다.
- 인접 섹션이 **하나의 배경을 공유**해야 하면 섹션마다 칠하지 말고 **감싸는 wrapper가 한 번만** 그린다(`.parts-group` 방식). 섹션마다 칠하면 경계에서 색이 끊긴다.
- 예외 — **카드·패널**은 당연히 `section-wrap` 안에서 폭이 제한된다. 이 항목은 **구간을 나누는 배경**에만 적용한다.

## 3. 움직이는 UI 목업 — 제품 화면이 살아 있는가

제품을 설명하는 페이지에 **정지된 스크린샷만 있으면** 제품이 죽어 보인다.
이 프로젝트는 목업을 실제로 돌아가는 화면처럼 보이게 하는 연출 6종을 **이미 갖고 있다.**

**기준 (실측)**

| 페이지 | 목업 연출 수 |
|---|---|
| index.html | 5 (stage 3 · detail 1 · ticker 1) |
| capability.html | 7 (ticker 5 · detail 2) |
| ax-build.html | 1 (stage 1) |

- **제품 화면을 보여주는 페이지에 `data-mock-motion`이 0개면 검토 대상이다.**
  정지 이미지로 둔 이유가 있으면 보고에 남기고, 없으면 연출을 붙인다.
- 연출은 **새로 만들지 않는다** — `focus` · `replay` · `deck` · `detail` · `ticker` · `stage` 6종에서 고른다.
  부모에 `data-mock-motion` 값만 주면 동작한다 → [mock-motion-guide.md](../mock-motion-guide.md)

```bash
# 이 페이지에 목업 연출이 몇 개인지
grep -o 'data-mock-motion="[a-z]*"' {페이지}.html | sort | uniq -c
```

**QA 시 흔한 오판 2가지:**

- **빈 목업을 버그로 단정하지 않는다.** 모션 사이클 중 빈 프레임이 찍힐 수 있다.
  스크린샷 한 장으로 판단하지 말고 몇 초 두고 다시 본다.
- **`stage`는 한 번만 재생된다**(의도된 동작). 다시 보려면 JS가 되감아야 한다 — 반복되지 않는다고 고치지 않는다.

## 4. 애니메이션 — 있는가, 그리고 절제되어 있는가

**없으면 죽은 화면이고, 많으면 산만하다.** 둘 다 실패다.

**있어야 하는 것**

| 자리 | 연출 | 확인 |
|---|---|---|
| 모든 섹션 | `fade-up` 진입 | `<section class="… fade-up">` — 섹션 수와 대략 같아야 한다 |
| hero | 로드 직후 순차 상승 | `fade-up.js` 대상이 아니므로 CSS 애니메이션으로 직접 |
| 카드 목록 | 순차 지연(stagger) | 항목 `.03s`, 큰 단계 `.1s` 간격 |
| 카드 hover | `translateY(-3px)` + 그림자 `sm`→`md` | 이 프로젝트의 표준 부상 폭 |
| 화살표 hover | `translateX(3px)` | |

```bash
# 섹션 수와 fade-up 수를 비교한다 (hero 제외라 1 적은 것이 정상)
grep -c "<section" {페이지}.html; grep -c "fade-up" {페이지}.html
```

**절제 기준 — 넘으면 산만하다**

- **한 화면(뷰포트)에 동시에 움직이는 요소는 3개까지.** 그 이상이면 시선이 흩어져 아무것도 안 읽힌다.
- **무한 반복 애니메이션은 한 섹션에 1개까지.** 계속 움직이는 것이 둘 이상이면 본문을 읽을 수 없다.
- **hover가 아닌 자동 움직임에 큰 이동을 주지 않는다** — 왕복은 `3px`, 주기 2~3s가 이 프로젝트의 리듬이다.
- **`--duration-hover: 0.1s` / `--duration-scroll: 0.5s` 이중 리듬을 지킨다.**
  hover가 느리면 굼떠 보이고, 스크롤 연출이 빠르면 급해 보인다.

**`prefers-reduced-motion` — 빠뜨렸으면 그 애니메이션은 추가하지 않은 것과 같다**

```bash
# 애니메이션을 넣은 파일에 대응이 있는지 짝을 맞춰 센다
grep -rln "animation\|transition" css/components css/pages | while read f; do
  grep -q "prefers-reduced-motion" "$f" || echo "대응 없음: $f"
done
```

## 5. 색·위계 — 3층으로 만들었는가

**위계는 배경 하나로 만들지 못한다.** 배경 · 카드 · 경계선 **3층**으로 만든다.

| 판 | 그 위의 카드 | 이유 |
|---|---|---|
| 흰 면 | `sunken` 카드 | 카드가 가라앉아 구분된다 |
| 옅은 면(`tint-2`) | **흰 카드** + 옅은 브랜드 경계선 | 카드가 떠 보인다 |
| 어두운 판 | 반투명 유리 카드 | 배경 질감이 비쳐 깊이가 생긴다 |
| 목업·대시보드 | **흰 바탕**에 둔다 | 그림자로 떠 있어야 하는 것 |

- **카드와 섹션 배경이 같은 색이면 카드가 사라진다.** 매번 확인한다.
- **배경색을 넣었으면 `dot-line`(점선 구분)은 뺀다.** 영역 구분은 border보다 background 차이로 한다 — 둘을 함께 쓰지 않는다.
- 다 했는데도 평평하면 **배경을 더 칠하지 말고** 아이콘·모션으로 넘어간다. 옅은 톤을 하나 더 추가하는 것으로는 해결되지 않는다.

**타이포 위계** — 크기로만 만들지 않는다. 크기는 [SKILL.md](../SKILL.md) 3번 제약(최소 14px · weight 3단)에
묶여 있으므로, **색(`--color-ink` 4단)** 으로 위계를 만든다.
같은 크기·같은 색 텍스트가 세 줄 이상 이어지면 스캔이 안 된다.

## 6. 구조·배치

- **섹션마다 좌우 여백이 같은가** — 데스크톱 80px · 900px 이하 20px. 한 섹션만 어긋나면
  그 섹션이 `.section-wrap`을 안 쓰거나 자체 padding을 갖고 있다는 뜻이다.
- **가로 스크롤이 없는가** — `documentElement.scrollWidth <= clientWidth`.
  (원인 3종과 해법 → [responsive-motion.md](responsive-motion.md))
- **비슷한 섹션이 연달아 3개 이상 오지 않는가** — 카드 3열이 세 섹션 연속이면
  스크롤해도 진도가 안 나가는 느낌이 든다. 레이아웃(1열·2열·목록·목업)을 번갈아 쓴다.
- **CTA가 경쟁하지 않는가** — `btn-primary`는 **한 화면에 하나**다.
  카드마다 primary 버튼을 두면 최하단 `cta-final`이 묻힌다(밝은 배경 카드면 `btn-ghost`).

```
- 강조 섹션: 어두운 판 2곳(outcomes, cta-final) — 기준 충족

- prefers-reduced-motion: 신규 2개 파일에 대응 추가

```
